# lab_manager

Telegram-менеджер лабораторных работ. Принимает задания, раскладывает их по папкам,
синхронизирует с Яндекс Диском, ведёт статусы и готовит промпты для агента-исполнителя.
Саму лабу не выполняет. Подробности — в [REQUIREMENTS.md](REQUIREMENTS.md).

> Статус: MVP работает в Docker — бот, приём заданий, Яндекс Диск, GigaChat, промпт для исполнителя.

## Требования

- Python 3.12+, [uv](https://docs.astral.sh/uv/)
- Docker (rootless) с `docker compose` — для запуска в контейнере

## Запуск (Docker)

```bash
cd ~/projects/lab_manager
cp .env.example .env && chmod 600 .env   # заполнить секреты
docker compose up -d --build             # сборка и запуск
docker compose ps                        # статус и healthcheck
docker compose logs -f lab_manager       # логи
docker compose down                      # остановить (данные остаются в томе)
```

- Данные (SQLite, папки лаб, кеш) — в именованном томе `lab_manager_lab_data`, путь в контейнере `/data`.
- Секреты — только через `env_file: .env`, в образ не попадают (`.dockerignore`).
- Сертификат Минцифры монтируется только для чтения; путь на хосте —
  `GIGACHAT_CA_HOST_FILE` (по умолчанию `/home/agent/certs/Russian_Trusted_Root_CA.cer`).
- Лимиты: 640 МБ памяти, 0.75 CPU; корневая ФС только для чтения, `cap_drop: ALL`,
  `no-new-privileges`; `restart: unless-stopped`; healthcheck — `python -m lab_manager health`
  (свежесть файла-пульса, который бот обновляет каждые 30 с).
- Портов нет: Telegram — polling.
- Резервная копия тома: `docker run --rm -v lab_manager_lab_data:/data -v "$PWD":/backup python:3.12-slim tar czf /backup/lab_data.tgz -C /data .`

Одновременно должен работать только один экземпляр бота (один токен = один polling).

## Разработка

- Интеграции со сторонними сервисами — строго TDD (тест первым); остальной код — тесты сразу после.
- `uv run pytest` — быстрые тесты на моках (живые исключены по умолчанию).
- `uv run pytest -m live` — живые тесты с реальными API (нужен `.env`), работают во временной
  папках `<YANDEX_DISK_ROOT>/_live_test_<uuid>` и удаляют их.

## Хранилище

SQLite в `$DATA_DIR/lab_manager.db` (WAL, внешние ключи включены). Схема — SQL-миграции в
`src/lab_manager/db/migrations/NNNN_<name>.sql`, применяются при старте по `PRAGMA user_version`.
Новая миграция — новый файл со следующим номером; старые не редактируются.

## Приём заданий

Конвейер: `sha256 → markitdown → извлечение полей → БД + папки`. Повторная отправка того же
файла ничего не делает; новый файл для той же лабы сохраняется как следующая версия.

Форматы: PDF, DOCX, PPTX, XLSX, HTML, TXT, MD (до 20 МБ). Сканы без текстового слоя
сохраняются с предупреждением (OCR — позже).

Короткий промпт к заданию:

```
<Предмет>, лаба <N>[, до ДД.ММ[.ГГГГ] [ЧЧ:ММ]][, <название>]
ОС, лаба 3, до 25.10
Базы данных; ЛР №2; сдать до 01.11.2026 18:00; Индексы
```

Номер, название и срок, если их нет в промпте, ищутся в самом документе.

Задание можно прислать и без файла — текстом (например, переслать пост преподавателя): текст
сохраняется как `задание/v1_задание.md`. Одно сообщение может описывать несколько лаб
(«ЛР 3 и ЛР4», «лабы 3, 4», «ЛР 3-5» в подписи или несколько лаб в тексте) — каждая
создаётся или обновляется со своими деталями. Номера из подписи важнее текста; если подпись
и текст расходятся (подпись «ЛР 4», в посте «ЛР 3»), результат помечается `low_confidence`,
и бот просит подтверждение. Этапы одной лабы отдельными лабами не становятся.

Раскладка (локально в `$DATA_DIR/Лабы`, затем зеркало на Диске):

```
<Предмет>/<NN> <Название>/
  задание/v1_<файл>, v2_<файл>, assignment.md
  requirements.md   # требования владельца (общие / предмет / лаба)
  prompt.md         # готовый промпт для исполнителя (Claude и др.)
  lab.json          # контракт для исполнителя (schema_version 1)
  отчёт/            # сюда исполнитель кладёт результат
```

## Яндекс Диск

Лаба зеркалируется на Диск (`YANDEX_DISK_ROOT`, например `app:/Лабы` при доступе только к
папке приложения — на Диске это `Приложения/<имя приложения>/Лабы`). Приём задания в той же
транзакции ставит задачу `disk_sync` в очередь (transactional outbox); обработчик очереди
выгружает оригиналы и `assignment.md`, пропуская файлы с совпадающим sha256, и создаёт `отчёт/`.
Ошибки 429/5xx повторяются с backoff, после 3 неудачных попыток задача помечается `failed`.

## GigaChat

Поля лабы извлекаются гибридно: явные поля промпта (номер, срок) — правилами, остальное
(название, краткое содержание, артефакты, предмет) — GigaChat через принудительный вызов функции
`save_lab` с проверкой pydantic-схемой. Модель возвращает дату «как в тексте», год досчитывает код
(модель не знает текущую дату). Номер из заголовка «Лабораторная работа №N» важнее ответа модели,
расхождение снижает уверенность. Документ передаётся в `<document>` как данные, с напоминанием
до и после (защита от prompt injection). Невалидный ответ возвращается модели с ошибкой;
если не помогло или API недоступен — работают правила.

- Системный промпт: `src/lab_manager/prompts/extract_lab.md`, версия `PROMPT_VERSION` в
  `extraction/llm.py` — при изменении промпта её нужно поднять (сбрасывает кеш).
- Кеш ответов (`llm_cache`) и журнал вызовов с токенами и ошибками (`llm_calls`) — в SQLite.
- TLS — по сертификату Минцифры из `GIGACHAT_CA_BUNDLE_FILE`.

## Промпт для исполнителя

`prompt.md`, `lab.json` и `requirements.md` собираются детерминированно (без LLM) из БД и
`assignment.md` по шаблону `src/lab_manager/prompts/executor.md`. Требования задаются на трёх
уровнях — общие, по предмету, к лабе (приоритет: лаба > предмет > общие); изменение пересобирает
промпты затронутых лаб и ставит выгрузку на Диск только если содержимое изменилось.
`lab.json` — стабильный контракт для исполнителя; несовместимые изменения — только с новым
`schema_version`. Текст задания вставляется в `<assignment>` как данные; закрывающий тег внутри
текста экранируется.

## Работа с ботом

- `/start` — справка и постоянные кнопки **📚 Лабы** / **📅 Неделя**.
- 📚 Лабы → предмет → лаба → карточка с кнопками: статус, 📄 промпт, 📝 задание, 📋 требования,
  ✏️ изменить, 🗑 удалить. Открытая карточка — «текущая лаба» для свободного текста.
- Задание: файл или пересланный пост + подпись «Предмет, ЛР N[, до ДД.ММ]» (до или после пересылки).
- Свободный текст: «что сдать на этой неделе?», «что нужно сделать в ЛР 4?», «лаба 4 в работе»,
  «это ЛР 4, а не 3», «срок 30.10 18:00», «перенеси в предмет ОС», «требования: вариант 7».
- Изменения после чтения текста задания (возможная инструкция из методички) требуют подтверждения кнопкой.
