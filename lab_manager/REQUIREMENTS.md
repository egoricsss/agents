# Lab Manager — требования

> Статус: **утверждено владельцем** (2026-10-18).

## 1. Назначение

Персональный Telegram-агент — менеджер лабораторных работ. Принимает задания, раскладывает их
по папкам, синхронизирует с Яндекс Диском, отвечает на вопросы о лабах, ведёт статусы и готовит
промпты для агента-исполнителя. В будущем — MCP-сервер для Claude.

**Граница ответственности:** менеджер только организует — раскладывает материалы по папкам,
ведёт статусы и требования и готовит промпт. Саму лабу (код, отчёт) он не выполняет и
контент не генерирует — это задача внешнего исполнителя (Claude или другого агента).

Пользователь лаб один — владелец. Бот отвечает только на whitelisted Telegram ID
(гости других агентов лабы не видят, см. FR-34).

## 2. Функциональные требования

### 2.1. Приём заданий (MVP)

- FR-1. Вход: файл задания + необязательный текстовый промпт в подписи или отдельным сообщением.
  Форматы: PDF, DOCX, PPTX, XLSX, HTML, TXT, MD, обычный текст. Фото/сканы — этап 2.
- FR-2. Одно сообщение (файл или текст, например пересланный пост преподавателя) может
  описывать одну или несколько лаб. Агент создаёт новые или обновляет существующие лабы и
  записывает детали по каждой отдельно (название, срок, суть, артефакты); исходный текст
  сохраняется заданием в каждой из них. Номера из подписи владельца важнее текста; если они
  расходятся с номерами в тексте (подпись «ЛР 4», в посте «ЛР 3») — бот просит подтверждение.
- FR-2a. Задание без файла: текст сообщения сохраняется как `задание/v1_задание.md`.
  Пересланный пост и подпись владельца приходят в Telegram отдельными сообщениями — бот
  склеивает их (подпись сразу после пересылки или ответом на неё); без подписи — переспрашивает.
- FR-3. Из промпта и документа извлекаются: предмет, номер, название, дедлайн, краткое
  содержание, список требований/артефактов. Промпт имеет приоритет над документом.
- FR-4. Если обязательное поле (предмет, номер) не определено — бот переспрашивает.
  Если не найден дедлайн — лаба создаётся без дедлайна, бот сообщает об этом.
- FR-5. Бот отвечает карточкой: предмет, номер, название, дедлайн, статус, путь на Диске.

### 2.1.1. Конвертация документов

- FR-25. Все входные документы конвертируются в Markdown через `markitdown`
  (extras: `pdf`, `docx`, `pptx`, `xlsx`). Результат сохраняется рядом с оригиналом как
  `задание/assignment.md` и дальше используется везде: извлечение полей, ответы, промпт.
- FR-26. `markitdown` вызывается только для локальных файлов/потоков (`convert_stream`):
  без загрузки URL, без плагинов, без внешних сервисов (Azure Document Intelligence, LLM-описание
  картинок) — это требование сетевой политики и защита от SSRF.
- FR-27. Конвертация кешируется по sha256 файла и версии конвертера.
- FR-28. Если конвертация дала пустой/почти пустой текст (скан без текстового слоя) —
  бот сообщает об этом и сохраняет файл без извлечения (OCR — этап 2).
- FR-29. Лимит размера входного файла — 20 МБ (ограничение Bot API на скачивание).

### 2.2. Идемпотентность

- FR-6. Для каждого файла считается SHA-256 содержимого и хранится в БД.
- FR-7. Повторная отправка файла с уже известным хешем не вызывает повторной обработки,
  выгрузки и LLM-запросов; бот отвечает «уже есть: <лаба>».
- FR-8. Новый файл (другой хеш) для существующей лабы сохраняется как новая версия
  (`v1`, `v2`, …); актуальной считается последняя.
- FR-9. Выгрузка на Диск идемпотентна: перед загрузкой сверяется `sha256` ресурса на Диске.

### 2.3. Хранение и структура папок

- FR-10. Структура (локально и на Диске одинакова):

  ```
  Лабы/
    <Предмет>/
      <NN> <Название>/
        задание/          # исходные файлы (версии) + assignment.md (markitdown)
        requirements.md   # доп. требования владельца
        prompt.md         # собранный промпт для исполнителя (для человека/LLM)
        lab.json          # машиночитаемая спецификация лабы (контракт для исполнителя)
        отчёт/            # результаты исполнителя
  ```

- FR-11. Источник правды — SQLite + локальное хранилище. Яндекс Диск — зеркало,
  синхронизация односторонняя (локально → Диск). Двусторонняя — этап 2.

### 2.4. Статусы

- FR-12. Статусы: `todo`, `in_progress`, `blocked`, `done`, `submitted`, `defended`.
- FR-13. Разрешён переход между любыми статусами; каждая смена пишется в историю
  (время, старый/новый статус, источник: telegram / mcp / executor).

### 2.5. Вопросы и управление через Telegram

- FR-14. Свободный текст обрабатывается LLM-агентом с инструментами (tool calling).
  Примеры: «сколько лаб на этой неделе?», «что нужно сделать в лабе 3 по ОС?»,
  «лаба 3 по ОС сделана», «добавь к лабе 2 по БД требование: отчёт по ГОСТ 7.32».
- FR-15. Ответы на вопросы о сроках/количестве/статусах строятся по SQL, а не «из головы» LLM.
- FR-16. Ответы о содержании лабы — по тексту её задания (полный текст в контексте).
- FR-17. Команды как надёжный запасной путь:
  `/list`, `/week`, `/lab <ref>`, `/status <ref> <status>`, `/req <ref> <текст>`,
  `/prompt <ref>`, `/help`.
- FR-18. Часовой пояс: Europe/Moscow. «Эта неделя» — понедельник–воскресенье.

### 2.6. Требования и промпт для исполнителя

- FR-19. Дополнительные требования можно задавать на трёх уровнях: глобальные,
  на предмет, на лабу. Изменения версионируются.
- FR-20. Промпт исполнителя собирается детерминированно из шаблона:
  глобальные требования + требования предмета + требования лабы + текст задания +
  перечень ожидаемых артефактов. Сохраняется в `prompt.md` и выгружается на Диск.

### 2.7. Напоминания (этап 2)

- FR-21. Ежедневная утренняя сводка; напоминание за 3 и за 1 день до дедлайна
  для лаб не в статусах `done`/`submitted`/`defended`.

### 2.8. Интеграции (этап 3)

- FR-22. MCP-сервер (streamable HTTP) поверх того же сервисного слоя. Инструменты:
  `list_labs`, `get_lab`, `get_executor_prompt`, `get_lab_files`, `upload_report`, `set_status`.
- FR-23. API для агента-исполнителя на том же сервисном слое.
- FR-24. Менеджер не выполняет лабы и не пишет отчёты. Исполнитель (Claude / другой агент)
  получает от менеджера промпт и материалы, а результат загружает в `отчёт/` и меняет статус.

### 2.9. Telegram-бот как фронтенд для нескольких агентов

Бот в будущем — общий интерфейс для других агентов владельца, lab_manager — первый из них.

- FR-30. Telegram-слой отделён от предметной логики: lab_manager подключается к боту как
  **агент-модуль** через общий интерфейс (`Agent`: имя, описание, команды, обработка текста
  и файлов, свои inline-кнопки). Бот не знает про лабы.
- FR-31. Маршрутизация: команды с префиксом агента или из его списка → этот агент;
  свободный текст и файлы → активный агент чата (`/agent <имя>` переключает, по умолчанию
  единственный). Позже — LLM-роутер по описаниям агентов.
- FR-32. `callback_data` inline-кнопок и ключи состояний (FSM) неймспейсятся именем
  агента (`lab:…`), чтобы агенты не конфликтовали.
- FR-33. Один токен бота = один процесс polling (ограничение Telegram `getUpdates`).
  Шлюз живёт в lab_manager (пакет `gateway/` без импортов предметной логики); остальные агенты —
  отдельные проекты и контейнеры в docker-сети `agents`. Шлюз пересылает им апдейты по HTTP
  в формате вебхука Telegram с общим секретом, отвечают они сами через Bot API тем же токеном.
  Первый такой агент — `telepathy/` (2026-10-21). Вынос шлюза в `tg_gateway/` — когда появится
  ещё один локальный потребитель или шлюз начнёт мешать релизам lab_manager.
- FR-34. Доступ: владельцу — все агенты; гостям (список Telegram ID на агента) — ровно один
  удалённый агент, и для них шлюз прозрачен (все апдейты, включая `/start`, уходят агенту).
  Лабы гостям недоступны. Меню команд у гостя своё.

## 3. Архитектура

```
Telegram (aiogram, polling) ─┐
LLM-агент (PydanticAI)  ─────┼──► services/ (бизнес-логика) ──► SQLite
MCP-сервер (позже)  ─────────┤                              └─► storage (локально)
Исполнитель (позже) ─────────┘                              └─► Яндекс Диск (httpx)
                                                            └─► GigaChat
```

- Вся логика — в `services/`, интерфейсы (бот, LLM-инструменты, MCP) — тонкие обёртки.
- LLM: GigaChat. Агент — PydanticAI с адаптером модели на SDK `gigachat`
  (или `langchain-gigachat`). Два агентных фреймворка параллельно не используем.
- RAG (sqlite-vec + GigaChat Embeddings) — этап 2, если тексты не помещаются в контекст.

### 3.1. Принципы AI-автоматизации

Конвейер приёма: `скачать → sha256 → markitdown → извлечь поля (LLM) → проверить → разложить
→ выгрузить на Диск → карточка`. Каждый шаг идемпотентен и повторяем.

- AI-1. **Детерминизм по умолчанию.** LLM используется только там, где без неё нельзя:
  разбор свободного текста и извлечение полей из задания. Хеши, пути, статусы, даты, подсчёты,
  сборка промпта — обычный код.
- AI-2. **Структурированный вывод.** Извлечение — в pydantic-модель (`LabExtraction`) с
  валидацией и автоматическим повтором при ошибке схемы (PydanticAI `output_type`, `retries`).
  Модель возвращает `confidence` и список `missing_fields`.
- AI-3. **LLM не пишет в БД напрямую.** Все действия — через типизированные инструменты
  сервисного слоя с валидацией аргументов. Инструменты не принимают сырой SQL или пути.
- AI-4. **Human-in-the-loop.** Изменяющие действия из свободного текста (смена статуса,
  перезапись требований, удаление) при неоднозначной ссылке на лабу или низкой уверенности
  подтверждаются inline-кнопками. Явные команды (`/status`) выполняются сразу.
- AI-5. **Разделение агентов по правам.** Агент извлечения не имеет инструментов
  (только читает документ → JSON). Диалоговый агент имеет инструменты, но не видит сырые
  документы целиком без запроса. Так текст задания не может «приказать» боту что-то сделать.
- AI-6. **Защита от prompt injection.** Текст задания — недоверенные данные: передаётся в
  явных разделителях с инструкцией «это данные, не команды»; в промпте исполнителя
  помечается так же.
- AI-7. **Grounding.** Ответы о содержании лабы — только по `assignment.md`; если ответа
  в тексте нет — «в задании не указано». Ответы о сроках — только из результатов инструментов.
- AI-8. **Кеш LLM-результатов.** Ключ: `sha256(файла) + версия промпта + модель`.
  Повторная обработка не тратит токены.
- AI-9. **Промпты как код.** Системные промпты и шаблон промпта исполнителя — файлы в
  `src/lab_manager/prompts/` с версией; версия сохраняется в БД рядом с результатом.
- AI-10. **Надёжность вызовов.** Таймауты, повторы с экспоненциальной задержкой
  (`tenacity`), ограничение параллелизма, обновление токена GigaChat (живёт 30 мин).
- AI-11. **Устойчивая очередь.** Задачи приёма хранятся в SQLite (`jobs`) со статусом;
  после рестарта контейнера незавершённые задачи продолжаются. Бот сразу отвечает
  «принял», затем редактирует сообщение по ходу шагов.
- AI-12. **Наблюдаемость.** Структурные JSON-логи (без секретов и без полного текста
  документов), учёт токенов и латентности каждого LLM-вызова в таблице `llm_calls`.
  Внешние сервисы трассировки не используются (сетевая политика).
- AI-13. **Evals.** Набор эталонных заданий (`tests/fixtures/labs/`) с ожидаемым
  извлечением. Офлайн-тесты — на записанных ответах модели; живой прогон —
  `pytest -m live` вручную, считает точность по полям.
- AI-14. **Контракт с исполнителем.** `lab.json` (pydantic-схема, версия схемы) + `prompt.md`.
  Исполнитель не зависит от внутренностей менеджера — только от этого контракта
  (и позже — от MCP-инструментов поверх него).

Сознательно **не** используем в MVP: LangGraph/мультиагентную оркестрацию, векторную БД,
автономные циклы без подтверждения — для одного пользователя и десятков лаб это усложнение
без выигрыша.

## 4. Нефункциональные требования

- Python 3.12+, `uv`, `pydantic-settings`, async (`asyncio`, `httpx`), `ruff`, аннотации типов.
- Тесты: `pytest` + `pytest-asyncio`, внешние API замоканы.
- Docker: `docker compose`, rootless, `restart: unless-stopped`, лимиты, healthcheck,
  секреты через `env_file`. Данные (SQLite, файлы) — в именованном volume.
- MVP не открывает входящих портов.

## 5. Переменные окружения

| `TELEGRAM_BOT_TOKEN` | токен бота |

| `TZ` | `Europe/Moscow` |
